团费监控脚本（tuan12355）代码讲解文档

本文档对工作区内全部 Python 脚本做逐文件、逐函数的讲解，说明每个函数用到的模块与方法，
并在第 9 章统一标注阅读代码时发现的问题与待确认项。

说明：本文档仅做讲解与标注，不包含任何代码修改。

1. 项目概览

这是一个「团费未缴监控 + 企业微信群提醒」的自动化脚本集合，用于定时登录「智慧团建」类管理后台，
查询下辖团支部的团费缴纳情况，把仍有团员未缴的支部汇总成一条提醒消息推送到企业微信群。

核心特征：

  • 定时触发：由外部调度器（crontab / Windows 任务计划程序）在 08:00 与 12:20 附近调用。
  • 有状态：用 state.json 记录「本月是否已缴清」「今天哪个时段查过了」，实现幂等，避免重复推送。
  • 单第三方库：只依赖 requests，其余全部是 Python 标准库。
  • 模块化：配置 / 登录 / 通知 / 主流程四层分离，main.py 是唯一入口。

notifier.py 28 向企业微信群机器人推送文本消息

即：config.py 是被三方共享的最底层常量模块，没有任何反向依赖，也不导入其他本地模块。

4. config.py —— 配置常量

本文件是纯常量模块，不含任何函数，被其他文件用 from config import ... 逐项导入。
导入时模块顶层代码会被执行一次，但这里只有赋值语句，副作用仅是将常量放入内存。

4.1 登录相关（第 6–11 行）

常量 值 / 含义

LOGIN_METHOD "GET" —— 决定 auto_login() 走 session.get 还是 session.post 分支

4.3 通用请求头（第 17–28 行）

COMMON_HEADERS 是一个 dict，被 session.headers.update() 一次性注入会话，之后每个请求自动携带。
各字段用途：

头部 作用
User-Agent 伪装成 Edge 浏览器（Chrome/155 + Edg/155），绕过简单的 UA 校验
Accept 声明期望返回 JSON
Accept-Language zh-CN 优先，符合中文用户特征
Origin / Referer 让服务端认为请求来自本站页面（跨域 XHR 的常规特征）
POWERED-BY-MENGXIANHUI: Approve ⚠️ 该后台系统的自定义标识头，通常是前端框架（梦先惠）带的，缺失可能被风控拦截
Connection: keep-alive 复用 TCP 连接，减少握手开销

4.4 企业微信通知（第 30–32 行）

常量 值 / 含义
WECHAT_WEBHOOK 群机器人地址 https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...，key= 后为占位符 你的key ⚠️ 未替换则发送必然失败
MENTION_ALL True，控制消息是否 @all 全体

4.5 定时（第 34–35 行）

常量 值 / 含义

5. login.py —— 自动登录

5.1 导入（第 2–8 行）

requests（建会话、发请求）、hashlib（MD5）、time（时间戳）、logging（日志），
以及 config 的 LOGIN_URL、LOGIN_METHOD、USERNAME、PASSWORD、COMMON_HEADERS。

用模块名（__name__ 即 "login"）创建子 logger。本模块不配置任何 handler，
实际输出由入口 main.py 的 logging.basicConfig 统一接管 —— 这是标准做法：
库模块只负责记录，入口负责配置输出目标。

5.2 double_md5(pwd: str) -> str（第 13–17 行）

作用：计算 md5(md5(明文密码))，模拟前端 JavaScript 的「两次 MD5」加密，服务端按此密文比对。

步骤拆解：

  1. pwd.encode() —— str 转 bytes。hashlib.md5() 只接受 bytes，传 str 会抛 TypeError。
  2. 内层 hashlib.md5(...).hexdigest() —— 返回 32 位小写十六进制字符串。
  3. .encode() —— 把该十六进制字符串再转回 bytes，作为外层输入。
  4. 外层 hashlib.md5(...).hexdigest() —— 得到最终结果。

方法说明：

  • hashlib.md5(data)：构造 MD5 哈希对象（不可逆摘要算法）。注意 MD5 已不适合做密码存储，
    此处是复刻既有系统的协议，不是自选方案。
  • .hexdigest()：以十六进制字符串形式返回摘要；对应的 .digest() 返回原始 bytes。

5.3 auto_login()（第 20–64 行）

返回：成功时返回 requests.Session 对象；失败返回 None。调用方靠 if not session: 判定。

分步讲解：

① 创建会话

  • requests.Session() —— 这是整个脚本的核心机制。Session 对象会自动保存服务端下发的
    Set-Cookie，并在后续同一 session 的所有请求中自动带上，同时复用底层 TCP 连接。
    登录成功后拿到的 SESSION cookie 就靠它自动携带，因此 main.py 只需把 session
    传给 query_tuanfei()，无需手动管理 cookie。
  • session.headers.update(dict) —— 会话级默认请求头，后续每个请求自动继承；
    单次请求传入的 headers 会与之合并，同 key 时请求级覆盖会话级。

② 访问主页“暖场”

先访问一次页面站，让服务端下发初始 cookie（部分系统要求先有会话）。整段包在
try/except 中，失败仅 logger.warning("访问主页失败（可忽略）")，不中断流程。

③ 计算加密密码与时间戳

  • time.time() 返回 float 秒级时间戳；* 1000 转毫秒，int() 截断小数，str() 转字符串。

④ 组装参数

  • weakPass: "0" —— 声明不使用弱密码通道（推测含义，取决于服务端实现）。
  • loginValidCode: "" —— 空验证码。
  • _: ts —— jQuery 风格的缓存穿透参数（jQuery 自动加 _=时间戳 防 IE 缓存），
    服务端通常忽略，但保留能更像真实前端请求。

⑤ 按方法分支发送

  • LOGIN_METHOD.upper() —— 大小写不敏感比较，避免配置写成 "get" 就失效。
  • data=params（POST）—— 以表单体（application/x-www-form-urlencoded）发送。
  • params=params（GET）—— 拼接到 URL 查询串。
  • timeout=15 —— 15 秒超时，防止请求挂死。

⑥ 状态码与响应解析

  • resp.raise_for_status() —— requests 的方法：HTTP 状态码为 4xx/5xx 时抛 requests.HTTPError，
    由外层 except 捕获。2xx 时静默通过。
  • resp.json() —— 按 JSON 解析响应体为 dict。若响应不是合法 JSON，抛 JSONDecodeError
    （requests.exceptions.JSONDecodeError，继承自 ValueError），同样被外层捕获。

⑦ 成功判定

用 .get() 而非 []，避免字段缺失时 KeyError。成功时：

  • session.cookies.get_dict() —— 把 RequestsCookieJar 转成普通 dict 便于打印与查键。
  • 即使没有 SESSION cookie 也只告警不失败，仍返回 session —— 这是一种「尽力而为」策略，
    代价是失败会推迟到后续查询接口时才暴露。

失败分支 logger.error + return None。

⑧ 异常兜底

捕获所有异常（含网络错误、超时、JSON 解析错误等），转成日志 + None，
保证调用方永远不会因登录问题崩溃。logger.info(f"登录返回: {result}") 会把完整响应体打进日志，
包含账号信息，见第 9 章问题 ⑦。

6. notifier.py —— 企业微信推送

6.1 导入（第 2–4 行）

requests、logging，以及 config 的 WECHAT_WEBHOOK、MENTION_ALL。
logger = logging.getLogger(__name__) 用法同 5.1。

6.2 send_wechat(content: str) -> bool（第 9–28 行）

作用：把一段文本推送到企业微信群机器人，返回是否成功。

① 构造报文

这是企业微信群机器人 Webhook 的固定报文格式：

  • msgtype —— 消息类型，"text" 表示纯文本（也支持 markdown、image、news 等）。
  • text.content —— 正文。
  • text.mentioned_list —— 要 @ 的成员列表；"@all" 表示全体成员。
    MENTION_ALL 为假时传空列表 []（表示不 @ 任何人）。

② 发送

  • requests.post(url, json=...) —— json= 参数会自动做两件事：
    1. 用 json.dumps 序列化 dict；
    2. 自动设置请求头 Content-Type: application/json。
      比手动 data=json.dumps(data) 更省事且不易漏设头。
  • ⚠️ 这里用的是模块级 requests.post（一次性短连接），没有复用 main.py 中登录用的
    session —— 这是合理的，因为企业微信与团费系统是不同的服务，cookie 不应混用。

③ 结果判定

企业微信接口用 errcode == 0 表示成功（HTTP 层通常恒为 200，业务错误在 body 里）。
失败时打印完整返回体便于排查（如 errcode: 45009 = 接口调用超过限制）。

④ 异常兜底

同样吞掉所有异常，返回 False，不向调用方抛出。

注意：本函数没有调用 resp.raise_for_status()，因此 HTTP 4xx/5xx 时 resp.json() 可能解析失败
并被 except 捕获，最终返回 False —— 结果正确，但错误信息不够精确。

7. main.py —— 主流程

7.1 导入（第 2–13 行）

标准库 json、os、sys、logging、time、datetime（同时导入 datetime 类与 date 类），
本地模块 config（4 个常量）、login.auto_login、notifier.send_wechat。

7.2 模块级日志初始化（第 15–25 行）

语句 说明
os.makedirs("logs", exist_ok=True) 创建 logs 目录；exist_ok=True 表示已存在时不报 FileExistsError
logging.basicConfig(...) 配置根 logger。注意它只在进程内首次调用时生效，后续调用被静默忽略。因此必须由入口调用，子模块不能调
level=logging.INFO INFO 及以上（INFO / WARNING / ERROR）都会输出，debug 被过滤
format=... %(asctime)s 时间、%(levelname)s 级别、%(message)s 正文。若写成 filename= 则是简化版单文件输出，此处用 handlers 是为了多目标
logging.FileHandler(...) 写文件。文件名 logs/{datetime.now():%Y-%m}.log 用 f-string 格式化 按月滚动（如 logs/2026-01.log）
encoding="utf-8" Windows 上必须，否则中文会乱码或抛 UnicodeEncodeError
logging.StreamHandler() 输出到 sys.stderr（注意不是 stdout），所以在控制台/重定向时留意
logger = logging.getLogger(__name__) 本模块 logger，向根 logger 传播

STATE_FILE = "state.json" —— 状态文件路径，相对当前工作目录，见第 9 章问题 ⑧。

7.3 状态读写

load_state()（第 31–41 行）

  • os.path.exists(path) —— 判断文件是否存在（也常用于判断目录）。
  • open(..., "r", encoding="utf-8") —— 文本模式读，显式 UTF-8（Windows 默认是 GBK，中文会崩）。
  • with 语句 —— 上下文管理器，保证异常时也能关闭文件句柄。
  • json.load(f) —— 从文件对象反序列化为 Python dict（对应 json.dump）。
  • 文件不存在时返回默认结构，五个字段的含义见第 8 章。

⚠️ 没有处理「文件存在但内容损坏」的情况（如上次写入被中断留下空文件），json.load 会抛
JSONDecodeError 导致整个脚本崩溃。见第 9 章问题 ⑥。

save_state(state)（第 44–46 行）

  • "w" 模式 —— 覆盖写，文件不存在则创建。
  • json.dump(obj, fp) —— 序列化到文件对象（对比 json.dumps 返回字符串）。
  • ensure_ascii=False —— 中文原样写入，而不是转成 \uXXXX 转义，便于人工查看。
  • indent=2 —— 2 空格缩进，人类可读。

7.4 时段判断

get_current_slot()（第 50–63 行）

作用：把当前时刻换算成「当天第几分钟」，在 CHECK_TIMES 里找出最接近且差值 ≤ 30 分钟的时段，
返回该时段字符串（如 "08:00"）；都不在窗口内返回 None。

关键方法：

  • datetime.now() —— 返回本地时区的当前 datetime（不是 UTC，见第 9 章问题 ⑨）。
  • .hour / .minute —— datetime 的属性，取时分。
  • slot.split(":") —— 按冒号切分成 ["08", "00"]。
  • map(int, ...) —— 对序列逐元素应用 int()，把字符串转成数字。
  • h, m = ... —— 序列解包，要求恰好两个元素。
  • abs() —— 内置函数取绝对值。
  • ±30 分钟容错窗口的意义：cron/任务计划的触发时间常有抖动或延迟，留窗口能保证仍落进对应时段。

边界说明：08:00 与 12:20 间隔 4 小时 20 分，窗口（各 ±30 分钟）不重叠，不会串时段。
若未来把两个时刻配得比 60 分钟更近，会出现「一个时刻被归到另一个时段」的抢占，见第 9 章问题 ⑩。

  • dict.setdefault(key, default) —— key 不存在时插入 default 并返回它；存在时直接返回现值。
    这里用于逐层构建嵌套结构，避免 KeyError。

9. 问题与待确认项标注

以下为阅读代码时发现的问题，按要求仅在此标注，未对代码做任何修改。

① 🔴 配置占位符未替换 → 脚本必然失败

config.py 第 11 行 PASSWORD = "你的真实密码"、第 31 行 WECHAT_WEBHOOK 的 key=你的key。
未替换时：登录返回失败（status != "OK"）→ 流程直接结束；推送必然 errcode != 0。

② 🟠 --force 无法真正强制运行

第 157 行的 this_month_done 判断在 force 判断之外无条件执行（第 145 行才有 not force）。
因此本月一旦判定「已缴清」，即使加 --force 也会在第 158–159 行提前返回。
如需真正的强制重跑，--force 也应跳过该判断。

③ 🟡 冗余导入

main.py 第 2 行 import requests：本文件未直接调用 requests 的任何 API。
第 10 行导入的 COMMON_HEADERS 在 main.py 正文中也未被使用。
均为无害冗余，可清理（清理不影响行为）。

④ 🟡 状态读写存在多次独立的读盘周期

is_slot_checked()（第 66–68 行）与 mark_slot_checked()（第 71–77 行）内部各自
load_state() 一次，与 run_check() 里已持有的 state 对象不是同一份内存对象。
当前不出错，是因为每次都在「读最新 → 改 → 写回」的完整周期内完成；
但第 203–208 行对 state 的修改与第 211 行 mark_slot_checked 的内部写入是两次独立落盘，
若中间进程被杀，可能造成两处不同步。属于可优化的设计点。

⑤ 🟠 需实测确认：团费查询的日期区间格式

第 82 行 date_str = f"{year_month}-{year_month}"，当 year_month = "202601" 时得到
202601-202601（起止月份相同）。该格式与参数名 date 的组合是否符合接口预期，
必须在真实接口上验证一次（常见变体：20260101-20260131、2026-01、或起止用不同参数名）。

⑥ 🟡 缺少异常防御的两处

  1. build_message()（第 121–125 行）用 item['name']、item['realTotal']、item['total']、
    item['unpaid']、item['unpaidAmount'] 直接下标取值，接口字段缺失/改名会抛 KeyError，
    导致整个流程在第 198 行崩溃（此时 session 已登录、数据已到手，却因渲染失败而白跑）。
    建议改为 .get(字段, 默认值)。
  2. load_state()（第 33–34 行）未处理 state.json 存在但内容损坏的情况
    （例如上次写入被强制中断留下空文件），json.load 会抛 JSONDecodeError 直接崩溃。

⑦ 🟠 日志可能泄露敏感信息

login.py 第 49 行 logger.info(f"登录返回: {result}") 会把登录接口的完整响应体写入
logs/*.log；第 54 行 logger.info(f"Cookie: {cookies}") 会把 SESSION cookie 明文写入日志。
若日志文件被共享/归档，等同于泄露会话凭据。建议脱敏或降到 debug 级别。

⑧ 🟡 相对路径依赖当前工作目录

STATE_FILE = "state.json"（第 27 行）、os.makedirs("logs")（第 16 行）、
f"logs/{...}.log"（第 21 行）均为相对路径。若调度器启动时的工作目录不是脚本所在目录，
状态与日志会写到别处，表现为「每次都是首次运行」和「找不到日志」。
建议部署时在命令里先 cd 到脚本目录（如 cd /path && python main.py），
或在代码中用 pathlib.Path(__file__).parent 拼绝对路径（后者涉及改代码）。

⑨ 🟡 时区依赖本机设置

datetime.now()（第 52、134 行）、date.today()（第 109 行）、time.time()（第 83 行）
均使用本机本地时区。若脚本运行在 UTC 时区的服务器上，「08:00」实际会是北京时间 16:00。
部署到境外/云服务器时需确认系统时区（或设 TZ=Asia/Shanghai）。

⑩ 🟡 时段与参数缺少校验

  1. --slot 的值（第 219–221 行）不做任何校验就原样写入 checked_slots。若手误传
    --slot 8点，会产生一条永不与 get_current_slot() 匹配的记录，该记录就失去了幂等作用。
  2. ±30 分钟窗口与 CHECK_TIMES 强耦合：目前 08:00 / 12:20 间隔 260 分钟，窗口不重叠。
    若将来把两个时刻配置得比 60 分钟更近，会出现「一个时刻被归到另一个时段」的抢占，
    导致实际的每日检查次数与配置不符。

⑪ 🟡 推送失败不重试

第 201–211 行：send_wechat 返回 False 时，代码依然 mark_slot_checked。
也就是说该时段的提醒机会已消耗掉，本次失败不会在本时段内自动补发，
只能等下一个时段（且若本次已把 history.notified 记为 False，也没有补偿机制）。
若希望更可靠，可改成「失败不标记时段，由下次调度重试」——但这需要配合重试上限，否则会刷屏。

⑫ 🟡 历史记录会被覆盖

第 204 行 state["history"][today] = {...}：同一天多次运行时，history 里当天的记录会被
最后一次覆盖，丢失中间过程。若需完整轨迹，应改为向 list 追加。
